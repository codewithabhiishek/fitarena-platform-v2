ROOT PROBLEM WITH OLD STREAK LOGIC
═══════════════════════════════════════════════════════════════════════════════

The original streak code in handle_submission_approved was technically present
but had these critical production flaws:

1. NO ROW LOCK — two concurrent approvals for the same user could both read
   the same streak value and both increment it, awarding a double-increment.

2. NO longest_streak — the DB schema had no column to track the all-time best
   streak, so "best streak" could only be approximated by the frontend.

3. update_user_streak RPC existed but was NEVER CALLED from the trigger —
   the trigger inlined its own streak logic (without the lock). The RPC was
   dead code, callable by the frontend which is a security hole.

4. current_date vs UTC — using current_date in the trigger picks up the DB
   server's local timezone, not UTC. Gyms in UTC+5:30 (India) could get
   wrong date comparisons around midnight. Fixed to use (now() AT TIME ZONE
   'utc')::date throughout.

5. No return value / logging — impossible to know if the trigger chose
   'increment', 'reset', or 'no_change' without instrumenting the DB.

WHAT CHANGED AND WHY
═══════════════════════════════════════════════════════════════════════════════

── src/supabase/schema.sql ──────────────────────────────────────────────────

users table:
  + longest_streak INTEGER NOT NULL DEFAULT 0
    Tracks all-time best streak. Updated atomically by update_user_streak.

leaderboard view:
  + longest_streak column exposed (was missing)

update_user_streak RPC (full rewrite):
  BEFORE: simple read-then-write, no lock, no longest_streak, used current_date
  AFTER:
    • Uses (now() AT TIME ZONE 'utc')::date for correct UTC date everywhere
    • Uses SELECT ... FOR UPDATE row lock → concurrent-safe, no double-increment
    • Updates longest_streak = GREATEST(longest_streak, new_streak) atomically
    • Returns 'no_change' | 'incremented' | 'reset' | 'first' for auditability
    • Four cases explicitly handled:
        CASE 1 (first ever):      last_active IS NULL     → streak = 1
        CASE 2 (already today):   last_active = today     → no-op
        CASE 3 (yesterday):       last_active = yesterday → streak + 1
        CASE 4 (missed day(s)):   any other date          → streak = 1

handle_submission_approved trigger (updated):
  BEFORE: inlined streak logic directly (no lock, no longest_streak)
  AFTER:
    • Delegates streak update entirely to update_user_streak RPC
    • RPC is called inside trigger (SECURITY DEFINER) → not callable standalone
    • Logs result with RAISE LOG for Supabase log visibility
    • All other logic (points, XP, level) unchanged

get_user_streak_status RPC (NEW):
  • Read-only RPC for UI to query streak state without exposing full users row
  • Returns: current_streak, longest_streak, last_active, streak_status, checked_at
  • streak_status ∈ { 'active_today', 'at_risk', 'broken', 'never' }
  • Frontend uses this for informational display only — never to set streak

── src/services/streakService.js (NEW) ──────────────────────────────────────

  Modular, pure utility functions for streak display:
    getStreakStatus(userId)          — calls get_user_streak_status RPC

STREAK ABUSE PREVENTION SUMMARY
═══════════════════════════════════════════════════════════════════════════════

Attack vector                   How it's blocked
─────────────────────────────── ─────────────────────────────────────────────
Frontend increments streak       Not possible — no frontend write path exists
localStorage manipulation        Not used — Supabase is sole source of truth
Multiple submissions same day    unique(user_id, challenge_id, submission_date)
                                 + update_user_streak CASE 2 no-op
Duplicate challenge spam         Unique partial index: one approved per user+challenge
Page refresh / login             Trigger only fires on submissions status change
Double-approval race condition   FOR UPDATE row lock in update_user_streak
Admin approves own submission    JS + DB RLS both block self-approval
Streak increment without approval Only path is trigger → status='approved' transition
